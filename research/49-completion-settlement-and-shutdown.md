# Completion settlement and shutdown

Reviewed: 2026-10-11. Status: source audit and primary-source research for the S-03B followup. The reviewed service runtime is unchanged from `f7396566708c4a4a5d66dfd887befa44e1d9f42a`; Decision0091 changes the client only. This note implements no retry, recovery or schema change.

## What needs to move together

The [analysis actor](../crates/sigy-service/src/control/actor/analysis.rs) removes recognition/translation workers before fallible settlement. An actual drained result can consequently be lost if settlement fails. The [actor dispatcher](../crates/sigy-service/src/control/actor.rs) then marks the service stopping. Merely leaving the finished worker in its original map would also leave `Pool::is_empty` false, so shutdown could wait indefinitely for a callback already consumed.

The recognition and [translation](../crates/sigy-service/src/storage/translations.rs) settlement paths perform their result, zero-USD decision, job-state and withdrawal-completion writes inside an immediate transaction. They read the job again after commit. A failure returned by that final read can follow a successful commit. Retry must therefore distinguish committed state from an uncommitted attempt rather than interpreting every error as rollback.

Recognition's successful terminal replay compares the stored output with the completion. Translation's terminal path validates job request/generation and returns the terminal job without the equivalent full result comparison. Before selecting exact retry semantics, audit translation artifact membership, cue contents and zero-USD receipt identity as well. Scheduling after successful settlement is a separate failure boundary: a later scheduling failure must not rerun a committed result.

The recognizer prepares the drained result before actor settlement; store publication itself performs no audio-file rename or scratch deletion. The [recognition executor](../crates/sigy-service/src/execution/asr.rs) and [translation executor](../crates/sigy-service/src/execution/translate.rs) attempt scratch removal before returning their envelopes, ignoring removal errors. An attempt that returns an error exits before that removal. Scratch absence therefore proves neither native drain nor successful settlement, and a retained completed outcome cannot promise to preserve scratch already removed. The first implementation still needs an audit of every early-return and launch-refusal path. The language-evidence followup is currently best effort after transcript publication, and cannot be described as part of that transcript transaction.

Original recording protection follows durable `analysis_jobs` state, not merely the actor map: [whole-recording deletion and segment release](../crates/sigy-service/src/storage/dvr.rs) exclude running/cancelling analysis jobs, and [pin replacement](../crates/sigy-service/src/storage/analysis.rs) refuses an active local recognizer. A failed pre-commit settlement retains those states; a committed terminal state can release that protection even if the subsequent read reports failure. Translation consumes stored cue text and has no equivalent original-media read. New retry slots must preserve these distinctions rather than adding a blanket media lease to every family.

The [withdrawal completion](../crates/sigy-service/src/storage/withdrawals.rs) transaction binds an existing native-stop target to the durable generation, attempt and lease owner, preserving observed and effective clocks separately. Work tokens expose immutable job/input identity but do not independently carry every pool claim field. The repair must bind and check claim authority deliberately, including outcomes with no withdrawal target. Existing [restart recovery](../crates/sigy-service/src/storage/job_pool.rs) leaves tracked unproven stops held while applying its separate legacy requeue policy; retaining an in-memory result must not change either contract implicitly.

## Upstream contracts

[SQLite result codes](https://www.sqlite.org/rescode.html#busy) distinguish competing-connection `BUSY` from same-connection/shared-cache `LOCKED`, and expose extended result codes. This distinction argues against a generic retry of every database error. Constraint, identity, integrity, disk-full and I/O faults cannot become silently retryable merely because they are wrapped as catalog errors.

[SQLite transactions](https://www.sqlite.org/lang_transaction.html) describe immediate write admission and commit/rollback behavior. A failed operation can require examining the actual transaction state; an application must preserve its own result identity across uncertainty. The locked [rusqlite 0.40.2 transaction contract](https://docs.rs/rusqlite/0.40.2/rusqlite/struct.Transaction.html) defaults to rollback on drop and offers explicit completion methods that report errors. These library contracts do not prove successful recovery from an unavailable filesystem.

## Proposed first repair boundary

Keep completed outcomes in a bounded slot separate from running worker liveness. Bind family, job, generation, attempt, claim authority and exact immutable input/profile/result identity. Running plus completed slots must fit the existing per-family pool cap. A completed worker consumes no new native execution, but its unsettled result and original-reader protection cannot disappear to make room for another claim.

Classify retryable errors explicitly. Freeze a finite attempt count, monotonic deadline and scheduling policy before code; use the existing actor/tick rather than an unbounded timer/task per failure. Audit the complete dispatcher: periodic reconciliation, another worker failure and explicit shutdown can race settlement. Preserve cancellation precedence and reject late generations. Read exact committed membership before retry after an uncertain result. Retrying publication never starts a recognizer/translator or creates another owner charge.

Define exhaustion and shutdown together. A hold needs useful inspection, retained protection and a finite shutdown outcome. Do not count an already finished native worker as live merely to retain its proof. Do not discard its only observed completion silently. If durable hold representation requires a new schema contract, specify and rehearse its populated migration before selecting that change. Uncommitted in-memory evidence is not reconstructible after process death; existing tracked uncertainty must stay held, and this work may not silently broaden legacy restart/requeue behavior.

Independent fixtures must cover rollback before publication, a commit followed by read failure, an exact committed retry, cancellation before retry, wrong generation/attempt/owner, classified busy versus nonretryable faults, retry exhaustion, another callback failing, and shutdown while a completed slot remains. Check artifact/decision counts, leases, finite allowances, slot occupancy, actual native launch count and bounded controller progress independently. Run faults only in disposable owned libraries.

The [near-term sequence](../docs/development/near-term-implementation.md#next-delivery-sequence) remains authoritative. This audit narrows the implementation questions; it establishes no new runtime evidence, automatic restart recovery or stage exit.
