# Local container boundary pilot

Reviewed: 2026-09-23. Docker Desktop 4.91.0 and Engine 29.8.0 were available on this Windows host after the user authorized startup. The Linux backend reported WSL2, cgroup v2, 16 virtual CPUs, and 32,494,989,312 bytes of memory. No containers existed before the probe. No image was pulled, model mounted, package fetched, or inference run. The full local command, image identity, observations, and cleanup receipt remain in ignored evaluation storage.

One trusted command ran from an existing image pinned by local image ID, with pulls disabled, no network, read-only root, UID/GID 65534, all capabilities dropped, no new privileges, no mounts or devices, 64 MiB memory, zero swap, 0.25 CPU, and 16 tasks. Inside the container, the effective identity and zero capability sets matched the request; `NoNewPrivs=1`, `Seccomp=2`, and cgroup files showed the configured memory, swap, CPU, and task limits. Only loopback appeared and the IPv4 route table was empty. A root-filesystem write failed. The command exited normally in 396 ms, reached a 5,193,728-byte cgroup memory peak, and the exact container was removed. This is one normal-path observation, not proof that every socket is denied or that cancellation and resource faults clean up.

No existing local image contains a qualified Whisper runtime. The retained runtime is a Windows executable archive, not a Linux worker. Before model execution, test socket denial, exact read-only file mounts, memory and process exhaustion, output caps, cancellation, deadlines, descendants, controller death, and recovery from an uncertain container state. Then qualify the Linux runtime and its loaded libraries, run bounded help, and try one verified audio clip. A container pilot does not qualify the native Windows product path or any language quality claim.
