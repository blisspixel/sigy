# Three-clip local recognition calibration

Run: 2026-09-24 on the development host (Windows 11 x86_64, Ryzen 7 7840U, about 64 GiB RAM). Scope: the first end-to-end recognition of the three selected FLEURS calibration clips, plus one generated silence control. This is calibration evidence for a research harness, not an application feature, a language-support claim, or a platform qualification. Holdout references were not opened.

## Decision basis

On 2026-09-24 the user chose to run pinned, hash-checked native recognition under enforceable Windows Job Object bounds now, and to record full operating-system network isolation as a stated limitation to close before the first complete release, rather than as a precondition for any model execution. The earlier AppContainer and at-creation job research remains the path toward that later gate.

## Execution boundary

A disposable harness launched `whisper-cli.exe` by absolute path from a private staged runtime directory, one process per clip, inside a ProcessKit 3.3.4 Job Object with:

- a process-count limit of 1 and kill-on-close;
- a committed-memory limit of 2 GiB (small) or 3 GiB (turbo);
- a CPU rate limit of 2 cores, with `-t 2 -p 1 --no-gpu`;
- a cleared environment containing only `SystemRoot` and a `PATH` of the runtime directory and `System32`;
- standard output and error each capped at 256 KiB, a 300 s wall deadline, and a check that the job had zero active processes afterward.

A static scan of `whisper-cli.exe`, `whisper.dll`, `ggml.dll`, `ggml-base.dll` and all nine CPU backend DLLs found no reference to `ws2_32`, `wsock32`, `mswsock`, `wininet`, `winhttp`, `urlmon`, `dnsapi` or `iphlpapi`. `ggml.dll` loads a CPU backend dynamically. This is static evidence only.

Every run exited 0 and every job was empty after teardown.

Language was auto-detected. Metrics: the frozen rule (NFC, whitespace folding, case and punctuation preserved) against the raw reference, and a supplementary loose rule (lowercase, punctuation removed) against the FLEURS normalized column. Silence control: without VAD, `small` emitted one segment with the text "you" and detected English. With the Silero VAD, both `small` and turbo emitted zero segments in under one second. A recognizer must not publish text for non-speech without a speech-activity gate; the product profile therefore requires VAD or an equivalent measured gate.

## Findings

- Real original-script text was produced for Arabic, Hindi and Spanish. Language identification was correct on all three speech clips.
- Turbo reduced Arabic loose CER from 11.1% to 1.7% and Hindi from 18.5% to 9.3%. Remaining Hindi errors are mostly spelling of long compounds and vowel signs.
- With two capped threads, turbo ran 6 to 16 times slower than real time on this host. The Spanish turbo run was markedly slower than the others; the cause was not isolated (thermal state and scheduling are candidates). Live use needs host-sized thread counts, and weaker machines need a smaller profile. No capacity claim follows from these runs.
- Peak committed memory stayed under 1.5 GB per job.

## Limitations

Three read-speech clips cannot qualify any language. No operating-system network denial was enforced; the claim is limited to the static import scan and the absence of network configuration. ProcessKit creates the child suspended and then assigns it to the job. Mapped-file and GPU memory are not bounded by the job commit limit. The small-model and turbo runs used the same runtime build. Canadian French, Navajo and Klingon are not covered.
