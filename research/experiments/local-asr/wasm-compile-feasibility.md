# WebAssembly recognition compile feasibility

Reviewed: 2026-09-23. This is a proposed compile-only experiment, not a selected or running recognizer. The [Windows native worker review](native-supervisor-design.md) has not found a safe wrapper that combines exact child-handle retention, token inspection and one-child resume. A core WebAssembly module hosted by Rust could instead give model code a strictly enumerated import surface. The host engine, compiler and operating-system libraries would still be trusted native code, and resource and cleanup behavior would need measurement.

[Wasmtime 49.0.0](https://github.com/bytecodealliance/wasmtime/releases/tag/v49.0.0) supports a Rust host on Windows and its stated minimum Rust version fits the selected 1.98.1 toolchain. The proposed host uses only `cranelift`, `runtime`, `std` and `reexport-wasmparser` with default features disabled. It supplies no WASI, HTTP, filesystem, process or guest-thread imports. A finite parser would require a core module with no start section, one non-shared memory capped at 2 GiB, bounded tables/functions and an exact export signature before safe module compilation. Import and resource inspection would precede any instance creation. Fuel, epoch interruption and an outer process deadline would need separate fault tests; [Wasmtime's interruption guidance](https://docs.wasmtime.dev/examples-interrupting-wasm.html) does not make blocking host calls interruptible.

The pinned [whisper.cpp API](https://github.com/ggml-org/whisper.cpp/blob/927cfce34f31707e17f2bff35c349632fb9e2c3a/include/whisper.h) exposes in-memory model initialization and PCM input, but its [browser build](https://github.com/ggml-org/whisper.cpp/blob/927cfce34f31707e17f2bff35c349632fb9e2c3a/examples/whisper.wasm/CMakeLists.txt) uses browser-specific binding, pthread and filesystem settings. It is not a drop-in offline module. A single-threaded CPU build from the pinned source and a narrow buffer ABI is the experiment. Source closure, C++ linking, imports, ABI layout and performance are unverified. The already retained publisher-hashed multilingual small model adds no download to the compile-only check and must not be opened by it. Radeon acceleration is outside this proposed CPU profile.

The official [WASI SDK 34 release](https://github.com/WebAssembly/wasi-sdk/releases/tag/wasi-sdk-34) provides a Windows x64 artifact, `wasi-sdk-34.0-x86_64-windows.tar.gz`. The [release metadata](https://api.github.com/repos/WebAssembly/wasi-sdk/releases/tags/wasi-sdk-34) reports asset ID `528366541`, exactly **619,003,408 bytes** and publisher SHA-256 `cccb5c323a9b34f0349a9b09e8804a0a7632c68c3310f4b5f437ed57d7e71d8f`. No SDK, Wasmtime crate, additional source or model asset was downloaded in this review. The archive still needs an exact checked transfer route, full member and legal-notice inventory, and qualified compiler/DLL closure before launch. The GitHub release signature does not independently sign the archive bytes.

The proposed maximum new response-body charge for the compile experiment is **971,324,944 bytes**: the exact SDK object plus bounded metadata, pinned source and resolved Rust crate objects. This is an envelope, not a reservation or authority for arbitrary downloads. The proposed additional working-storage admission is 16 GiB plus 2 GiB free-space headroom under the existing 100 GB cap. No new charge has been entered; the shared ledger remains at 22 rows and **13,608,843,985 policy bytes**, with USD 0 external spend. Exact objects and their licenses must be enumerated before any GET. The minimal Wasmtime Cargo graph, recursive whisper source closure, redirect path, archive member forms and compile supervision remain open.

The next proof is to qualify those exact assets, build the pinned source with the Windows SDK under bounded local supervision, and reject unresolved or unreviewed module imports. Only then should a safe Rust host compile the module without instantiating it. Synthetic authority and resource faults precede one real speech attempt. No elapsed-time, memory, language-quality or platform-support claim follows from this feasibility review.
