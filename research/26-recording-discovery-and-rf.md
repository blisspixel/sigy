# Recording, discovery and RF contracts

Reviewed: 2026-09-21. Research and implementation choices are distinguished below.

## Recording implementation choice

Hickory Resolver 0.26.3 supplies asynchronous resolution with system configuration. It removes the blocking name-lookup lifetime used by the earlier adapter. System configuration loading still uses platform APIs; this is not a claim that every OS operation is preemptible. Resolved addresses continue through Sigy's existing policy. [Resolver documentation](https://docs.rs/hickory-resolver/0.26.3/hickory_resolver/).

FFmpeg 9.0.1 is already installed on the available Windows host. Its local CLI and official documentation were checked for decoder threads, protocol restrictions, progress output and allocation controls. The initial adapter uses a supervised executable receiving local bytes, rather than linking its native libraries into the service. FFmpeg's `max_alloc` limits individual allocations, not total memory. [Official CLI reference](https://ffmpeg.org/ffmpeg-all.html), [license and distribution considerations](https://ffmpeg.org/legal.html).

Symphonia 0.6.1 remains a candidate for an isolated Rust media worker and later playback. It was not added: codec/platform coverage, malformed-input containment and playback integration still need evaluation. Using a pure-Rust decoder would not eliminate the need for resource and process controls. [Symphonia](https://docs.rs/symphonia/0.6.1/symphonia/).

Process-wrap 10.0.0 provides maintained process-group/job supervision. The selected features exclude its default tracing/session extras. SHA2 0.11.0 supplies maintained hashing; fs4 1.1.0 supplies free-space information. All choices use the existing runtime/catalog rather than a second worker framework. Their transitive graph includes platform crates, DNS caching and process support; minimal dependencies means justified dependencies, not ignoring this increase. Exact resolved versions live in Cargo.lock. [Process-wrap](https://docs.rs/process-wrap/10.0.0/process_wrap/), [SHA2](https://docs.rs/sha2/0.11.0/sha2/), [fs4](https://docs.rs/fs4/1.1.0/fs4/).

## Directory and podcast integration

Radio Browser exposes a free station catalog and federated mirrors. Its guidance uses DNS/SRV discovery of servers, randomized selection/failover, stable station UUIDs, country codes and an identifying user agent. Multiple mirrors are one data source, not independent evidence. [API discovery](https://api.radio-browser.info/), [federation notes](https://www.radio-browser.info/faq).

Proposed integration: a namespaced provider adapter, bounded refresh pages, conditional requests when supported, source-provided timestamps, local fetch time, stale/error status and atomic snapshot replacement. Preserve working cached results when refresh fails. Search/filter from the local index with visible provider and freshness. Directory updates may propose a new source revision; existing recording intent remains pinned. Cross-provider deduplication retains each origin rather than counting aliases as separate station coverage. Do not send listening history or optional popularity events implicitly.

Podcasts can start with publisher feed URLs without a directory account. RSS enclosures identify episode media; publisher identity and episode GUID remain distinct from the current download URL. Podcast Index offers another discovery API whose authentication and usage terms must be qualified before dispatch. Multiple discovery adapters can contribute to the same catalog while preserving provenance. [RSS specification](https://www.rssboard.org/rss-specification), [RSS profile](https://www.rssboard.org/rss-profile), [Podcast Index API](https://podcastindex-org.github.io/docs-api/).

Feed implementation must bound document size, parser nesting, episode count, refresh rate, backfill, redirects and enclosure bytes. Disable external entity/network resolution. Treat descriptions, transcripts and chapter resources as untrusted. A feed refresh is not blanket permission to download every enclosure or follow secondary URLs. Podcasts are now prioritized with internet radio before hardware, rather than deferred behind RF work.

## Review of supplied catalog and rich-feed research

The supplied research usefully identifies directory fields, stable episode identity, OPML portability and rich podcast resources. Its precise catalog totals, coordinate percentages, undocumented rate/clock-skew limits, and bulk-dump timetable have not been independently verified. Treat these as claims to check, not constants or service guarantees. Cache and request budgets are application policies unless supported by current provider documentation. Apple documents a search limit up to 200 results, not the claimed approximate 100. [Apple search parameters](https://developer.apple.com/library/archive/documentation/AudioVideo/Conceptual/iTuneSearchAPI/Searching.html).

Radio Browser requests click-counter calls from clients. The endpoint changes popularity state, so it is not an innocuous read-only URL refresh. Resolve its provider requirements and user-visible privacy controls before integrating click reporting. Autonomous monitoring, retries and batch refresh must not masquerade as human clicks or votes. [API reference](https://docs.radio-browser.info/).

Keep the selected Rust CLI/TUI and local controller. A secret configured by an individual user can stay in that user's service; this does not require a new hosted backend or distributing one shared application secret. Do not adopt the supplied blanket claims that playback never needs licensing, that recording is universally forbidden, or that directory metadata licenses authorize audio reuse. Retain the existing lawful-use scope and qualify each provider/distribution channel. Apple review rules are a distinct future distribution constraint, not a global legal ruling. [App Review Guidelines 5.2](https://developer.apple.com/app-store/review/guidelines/#intellectual-property).

On 2026-09-21, a bounded direct read of the [No Agenda feed](https://feeds.noagendaassets.com/noagenda.xml) returned 2,424,758 bytes, 239 episode items, 239 transcript references, 239 chapter references and one live-item element. The newest item was episode 1905, dated September 20, with an SRT transcript reference. This verifies that the current document is a useful rich-feed case. It does not verify transcript accuracy, secondary resource availability, directory IDs, live status, or every episode ever published. No enclosure, artwork, transcript or chapter asset was downloaded or copied into the repository.

Prefer suitable publisher transcripts before scheduling speech recognition, preserving publisher identity, language, revision and media alignment. Allow another derived transcript when captions are missing, incomplete, inaccurate, in a different language or explicitly reprocessed. Keep versions and comparisons rather than replacing the publisher artifact. Transcript selection considers requested language, timing, completeness and supported format; a universal VTT-over-everything ranking is insufficient. [Transcript specification](https://raw.githubusercontent.com/Podcastindex-org/podcast-namespace/main/docs/tags/transcript.md).

Correct tag semantics matter: `podcast:locked` concerns importing a feed into a different hosting platform, not an absolute prohibition on URL migration or client subscription. `podcast:block` specifies platform/public-ingestion preferences with platform-specific precedence. `liveItem` has pending/live/ended states; scheduled times alone do not establish that a stream is live. A show may have both episode and live-stream identities, and a live stream may also appear in a radio directory. [Locked](https://raw.githubusercontent.com/Podcastindex-org/podcast-namespace/main/docs/tags/locked.md), [Block](https://raw.githubusercontent.com/Podcastindex-org/podcast-namespace/main/docs/tags/block.md), [Live item](https://raw.githubusercontent.com/Podcastindex-org/podcast-namespace/main/docs/tags/live-item.md).

Plan bounded transcript and chapter retrieval, cue seeking, timed chapter metadata, and show/episode/chapter artwork references with terminal text fallbacks. Fetch secondary assets only through the same network and resource policy. Funding/value tags are metadata; they never authorize payments. Acceptance also needs sparse, malformed, multilingual, duplicate, moved, stale-live and oversized-feed cases. One richly populated English-language show cannot qualify general podcast support.

## RF interchange and capability discovery

The reviewed SigMF specification is v1.2.6. It defines sample representations, global metadata, capture segments and annotations, including frequency/sample-rate information and extension namespaces. This is a candidate interchange projection for IQ and real samples, not a replacement for application lifecycle and cost/retention policy. No compliance is claimed. [SigMF specification](https://sigmf.org/).

HackRF Pro and Meshtastic have distinct acquisition models. Receiver tuning/sample capabilities belong to the hardware profile; Meshtastic protocol messages and LoRa radio settings belong to separate layers. The available documentation informs the contract, but does not establish compatibility with the user's devices. [HackRF Pro](https://hackrf.readthedocs.io/en/latest/hackrf_pro.html), [Meshtastic radio settings](https://meshtastic.org/docs/overview/radio-settings/).

See the [metadata and receiver design](../docs/design/recording-metadata.md) for band browsing, CB presets, scans and signal detection. Those features require measured bandwidth/capacity, jurisdiction-specific band-plan review and physical receiver tests. They must not label incomplete scanning as full-spectrum coverage or interpret an RF peak as identified content.

The supplied hardware research gets the scanner/modem distinction right, but its fixed 8-bit/20 Msps description is incomplete for HackRF Pro. Official documentation also describes low-rate 16-bit extended-precision samples and a 4-bit mode up to 40 Msps. Discover and qualify the actual firmware/driver mode instead of encoding one universal format. The documentation identifies a hardware transmit-disable facility; using it requires device-specific verification. [HackRF Pro capabilities](https://hackrf.readthedocs.io/en/latest/hackrf_pro.html).

Official `hackrf_sweep` output contains frequency bins and dB values with one timestamp per complete sweep. Do not relabel these as calibrated dBm or simultaneous observations. Record sweep parameters and unobserved intervals; short transmissions may be missed. Energy detection cannot establish a LoRa protocol, payload, station identity or permission. Exact gain, front-end protection, antenna and firmware procedures need current device documentation before use. [Official tools](https://hackrf.readthedocs.io/en/latest/hackrf_tools.html).

The user's USB LoRa device has not been identified. Chip, band filtering, firmware, serial API and receive behavior must be inspected before promising raw LoRa, LoRaWAN or Meshtastic compatibility. A single-channel modem cannot be treated as a concentrator or spectrum receiver. Do not send configuration or join commands that might transmit during a receive-only discovery workflow.

Regional authorization is more specific than a universal license checkbox. For example, US CB rules describe operation without an individual license while still imposing operating and equipment requirements. This is not permission to transmit from arbitrary SDR hardware. Initial Sigy hardware adapters remain receive-only. [47 CFR Part 95, Subpart D](https://www.ecfr.gov/current/title-47/chapter-I/subchapter-D/part-95/subpart-D).
